# OneDrive account transport — ordinary directory layout (0.9.0)

This document supersedes the 0.8 immutable-content-directory design. Historical validation documents remain audit records, not the current storage contract.

## Restore verification, project health and bounded transport

Explicit `restore-list`, `restore` and `restore-test` are separate from comparison and transaction recovery. They discover current business files or the previous indexed archive, preserve the exact cloud identity/version and require trusted SHA-256 evidence before downloading. Downloads are version-checked before and after the transfer and hashed locally. Unknown evidence remains visible as insufficient evidence. Output uses create-only publication beneath an independent directory and rejects overlap with active/retired project sources, application, data and protection locations, as well as reparse points. No cloud content, baseline or mapping readiness is changed.

Restore tests create fresh run directories, retain verified files and a JSON report, and may use a byte budget and rotating groups. Oversized files are reported as skipped and must be checked with a larger budget. Budget rotation cursors are disposable cache, never recovery state. Successful sample evidence is stored in `state/devices/<device>/restore-verification/<binding>.json` and bound to device, account, drive, repository, management root, project and physical mapping. Its timestamp, scope and file count describe only the sampled content, not complete repository verification.

`ProjectRun.CoverageComplete` explicitly distinguishes a complete successful observation/execution from a successful partial selection. Current-mapping health in last-run summaries records complete success, known pending paths and their first observed times. Counts are lower bounds where work was not started or selected. Rule-only edits preserve binding; physical mapping changes isolate old health. Summaries only inform the UI and never authorize operations or cleanup. The UI shows independent complete-success and restore-verification times and deduplicates 24-hour stale/pending reminders.

Backup settings optionally contain `transfer.uploadKiBPerSecond` and `transfer.downloadKiBPerSecond`, each an integer in 0..1048576 (zero/unset means unlimited). A drive session shares one limiter per direction across all content streams, including metadata bodies. This is separate from automatic-run total-byte/duration budgets and Graph Retry-After handling. Pacing is cancellable and uses small chunks; deliberate upload pacing does not count as a stalled network request. Cloud-internal copies have no local body stream to limit.

Large file-evidence catalogs may use optional immutable checkpoints under `metadata/projects/<project>/checkpoints`. Checkpoints contain compact current evidence and version-bound summaries of the immutable source catalog; matching portions may be reused and changed portions are read from original evidence. Local copies are disposable cache. Checkpoints bind the account/drive/repository context and carry a content checksum. Missing, malformed, changed or insufficient checkpoint evidence triggers original-record reads. Full checks bypass checkpoints. Read-only observation never publishes checkpoints; successful complete execution may publish them periodically. Original file evidence, baselines, archives, conflicts and unresolved transactions are never removed by this optimization. Directory catalog enumeration remains necessary; the optimization reduces historical JSON body reads, not all work to constant time.

## Management repository format v2

repository.json and onedrive-account.json now use schemaVersion 2. CloudFolders contains only archives, conflicts and metadata. The former backups field and resolver branch are removed; existing backup contents are not moved or deleted. File metadata, project bindings, transaction and other configuration schema versions are independent.

A v1 account document is validated and normalized in memory on read; only an explicit save persists v2. A v2 folder object rejects obsolete or unknown members. Repository v2 requires all three folder names and rejects identity/layout mismatches.

Creating a new management repository writes v2. Applying cloud storage settings to an existing v1 repository (or CLI cloud-upgrade) validates its identity and layout, checks there are no pending local transactions, conditionally renames the original marker to .harborbackup-repository-v1.json, then creates and verifies the v2 marker before saving the local account settings. ID and management paths remain unchanged. The backup preserves the original bytes and is retained as upgrade evidence. Ordinary backup and preview reject v1 with upgrade instructions; they do not migrate implicitly.

The rename and create are not a distributed atomic operation. Between them, readers fail closed on the missing marker. If a response is lost, retry the same explicit Apply: a missing marker can resume from the validated v1 backup, and an already-created v2 marker can finish saving the local account. A pre-existing backup collision, unsupported schema or mismatched bound identity stops migration. No unconditional marker overwrite or data cleanup is used. Update/stop old clients before upgrading; old binaries reject v2 and cannot perform new validated runs. Already-running old operations must finish before the upgrade.

## Locations

Projects select a final folder relative to the authorized OneDrive root, e.g. Projects/DROP_CODE. The original file names, relative directories and empty folders are retained there. No computer name, project digest, revision ID or implicit backups prefix is inserted.

The separately selected HarborBackup management folder contains repository.json and:
- metadata/projects/<project-id>/locations/<mapping-id>.json: immutable version-3 location revisions under the stable project ID.
- metadata/projects/<project-key>/files/<operation-id>.json: immutable file evidence (SHA-256 from local transfer, item ID, ETag/cTag, size, provider checksum, source modification time, device).
- metadata/devices/<device>/<project-key>/<observation-id>.json: device run observations.
- archives/<project-destination>/<relative-file-path>: the last replaced complete file, preserving the original tree.
- conflicts/<project-destination>/<relative-parent>/<stem>.<device>.<operation-id><extension>: actual unresolved conflicts.
- metadata/protection/<archives|conflicts>/<project-key>/<path-key>/<operation-id>.json: protection identity, version and item mapping. Content directories contain no index.json or content layer.

Project keys are the stable 64-character hexadecimal project IDs from projects.json schemaVersion 2. Names, local sources, destinations and provider folder IDs are mutable properties. No path-derived project identity or old-project configuration migration is supported; fresh initialization and a new management repository are required.

Existing ordinary nonempty targets are allowed. Unconfirmed backup and pull defer files without trusted matching metadata. Ordinary pull and selected-project upload previews offer explicit per-file consent to use the chosen side, protecting replaced content first. Baseline establishment is part of execution rather than a separate configuration workflow. Unknown cloud content can be archived for an explicitly confirmed upload using its item identity and provider checksum; its protection record remains ContentHashKnown=false. Missing checksums stop replacement without silently downloading business content.

## Local mapping and configuration-only saves

projects.json schemaVersion 2 optionally stores global built-in exclusions in builtInExclusions (an array of versioned preset IDs, empty by default). Core owns the immutable preset catalog; Windows expands it together with global/project custom rules for both Desktop and CLI. Unknown IDs and malformed preset arrays fail validation, including configurations with no projects. New catalog items are never enabled implicitly; changing a published preset requires a new ID. Existing manual exclusion fields retain their meaning. Effective rules invalidate inventory and local hash caches, independently of mapping identity; selected IDs and original custom rules are also carried into previews to explain provenance. Adding or removing exclusions retains initialization, baselines, recovery evidence and existing business files. Reintroduced files use retained per-file baselines; unequal content without a common baseline or changes on both sides require an explicit choice for those files.

Desktop new-project onboarding runs a read-only cloud check before the configuration save. The selected physical folder is matched against the current repository catalog by folder ID. A single existing registration offers explicit continuation under its original project ID, keeping the chosen local source and exclusions; an already-local project or multiple registrations cannot be silently duplicated. An unregistered nonempty folder requires an initial read-only content review and explicit confirmation before saving. Cancellation, failed observation and stale folder selections do not save the draft or transfer business content. The resolved folder ID is retained in the mapping. Neither confirmation establishes a common baseline or activates automatic backup; a subsequent explicit upload/pull must complete. Editing existing projects retains the offline configuration-only save behavior below.

Saving project settings validates configuration structure and path relationships without requiring a live account, an existing local directory, a preview, or completion of pending transfers. It writes only configuration documents. Execution still validates account authorization, directory accessibility, links, and the live cloud target. Saving remains serialized with active operations and uses optimistic document signatures.

The stable project ID and cloud folder binding are independent of the local source path. New mappings or changes to the actual source/destination/folder get a fresh mappingVersion in projects.json. Rule-only edits retain their version; returning to a previous physical mapping still creates a new version. Active projects use bindingVersion 1 (direct-v3), which binds device, account, drive, repository, management root, project, source, destination, target, cloud folder and mappingVersion, excluding filter rules. Cloud location revision identities also exclude rules. The editor retains retiredMappings snapshots in the same atomic project document so existing v4/v5 journals remain discoverable even after a project is removed. These snapshots include the original device/account/repository context and resolved project paths/rules. They are local recovery metadata, never shared cloud metadata.

Baselines remain scoped to the mapping binding, and genuine new mappings do not inherit old evidence. Legacy snapshots omit BindingVersion and retain byte-compatible direct-v2 bindings/checksums. Reading a configuration without bindingVersion retains its exact legacy snapshot in memory; the next project save stores that snapshot and bindingVersion 1 atomically. Reads and saves do not copy, rewrite or delete state. To repair prior rule-induced resets, a session can read predecessor baselines newest-first, with current evidence taking precedence. Every predecessor is integrity checked and must match device/account/repository and physical project mapping. Traversal stops at a relocation, a different account/device or a new-format mapping-version change; only legacy rule-only transitions may cross mapping versions, after a validated legacy snapshot of the active mapping version establishes continuity. Removing and rejoining a project cannot skip confirmation merely because its rules differ from a retired legacy snapshot. Switching away and back therefore cannot revive an old mapping. Missing per-file records may fall back to older compatible records; malformed records fail rather than being skipped.

The state/devices/<device>/cloud/<binding>/mapping-ready.json acknowledgment records completion of the first explicit operation. Readiness can continue from a validated compatible predecessor, including retained state from a legacy versionless mapping. Missing proof on all eligible scopes or malformed acknowledgment requires manual initialization; malformed evidence never activates automatic backup. Partial selections with outstanding work, cancellation, errors and recovery-only runs do not activate a new mapping. The acknowledgment is state, not disposable cache. Local hash caches use a versioned envelope with an effective-rule signature, and inventory snapshots have their own rule signature; changing or reverting rules forces fresh observations without discarding baselines. Excluded pending transactions remain retained and may be explicitly recovered using their original evidence, but ordinary backup does not retry their excluded files.

The filter semantics follow the distinction in [rclone copy](https://rclone.org/commands/rclone_copy/) and [filtering](https://rclone.org/filtering/): scope selection does not imply removal of excluded destination files. [rclone bisync](https://rclone.org/bisync/#filters-file) requires resync after filter-file changes to prevent excluded entries being interpreted as deletions. HarborBackup never propagates deletion, so it refreshes filtered observations and preserves per-file common evidence instead of resetting the whole project.

Saving does not create the local root. Pull preview can inspect a missing destination without creating it; execution creates it when downloading or explicitly accepting an empty project. Backup requires an accessible source. Upload and pull confirmations bind the direction, mapping, relative path, local hash, baseline and cloud identity/version. Changed evidence is skipped, not overwritten under stale consent. Both directions preserve opposite-only files and do not propagate deletions.

New v5 journals carry an integrity-checked original mapping snapshot. Discovery validates the device, account, drive, repository, binding, journal location and format before recovery. Explicit recovery uses the snapshot's original source, never the newly selected source. Configuration and read-only observation do not require recovery. Pending operations defer only files whose cloud or local paths overlap the unfinished operation, including ancestor/descendant collisions; other files in the same project remain selectable and executable. Transfer commands retain existing pending operations rather than implicitly recovering them. Damaged recovery evidence permits observation but cannot authorize writes. The account-store pending-transaction guard covers changes to account, drive, repository ID, management root, enabled state and OAuth client ID; display names, retention and client-ID casing do not change binding identity.

Concurrent cloud location revisions at the latest generation must agree on one physical folder ID. Multiple records for that same folder are valid; divergent folders produce an explicit error before transfer instead of choosing a destination by record ID. The conflicting registration evidence remains available for review.

## Decisions without business-content downloads

Preview reports carry a direction-independent `VerificationCategory` per observed path, aggregate verification counts and a run-plan summary. `verify` forces fresh local hashing and marks Mode=Verify; differences, missing entries, type conflicts and unverifiable evidence give exit code 2 independently of whether a backup would copy them automatically. Equality is supported by local hashes and version-bound cloud metadata, not an independent hash of a downloaded cloud body. Explicit execution selections keep their existing per-file evidence checks.

Configuration-only previews attach `ConfigurationImpact`. Changed rules on an unchanged physical mapping compare candidate and original read-only observations, using stable project IDs and case-insensitive relative paths. Counts are estimates across two observations, not a locked snapshot; unreadable original/candidate observations or changed mappings use unknown counts. No state, baseline, business content or configuration is committed by this comparison; caches remain rebuildable. Offline saves do not require this optional preview.

File processing distinguishes FileUnavailable, Network, Authorization, RecoveryRequired, Budget and Cancelled. Only failures proven to occur during local preparation before business/state writes may continue dispatch as file-local errors. Errors during writes remain conservative: stop dispatch and retain transaction evidence. Existing known pending records continue to block only overlapping paths. Each project refreshes pending discovery so a preceding project's newly retained operations cannot be missed.

schedule.automaticMaxTransferMiB (0..1048576) and automaticMaxDurationMinutes (0..1440) default to zero/unlimited. They become a shared per-run `AutomaticRunBudget` only for automatic backup. A monotonic clock covers the whole run, including scan time; checks occur between operations and do not cancel in-flight reads or transfers. Content bytes are reserved atomically before applying each write plan, including local-content protection uploads; the last started file may exceed the size limit. Control metadata and cloud-internal copy overhead are excluded. Budget cutoff stops new dispatch and drains started work; it records a nonfailure budget issue and BudgetStopReason without cancellation or mapping initialization. Completion=BudgetLimited applies only in the absence of other file attention, with exit code 2; other failures and user cancellation retain precedence. The existing hard deadline remains independent.

The current directory is observed independently of metadata. Trusted file evidence must match item identity, size and ETag or content tag, with the provider checksum matching when present. Folder ETag changes are not treated as content corruption.

Three-way decisions use this device's confirmed common hash. One-sided changes can be backed up or pulled in the permitted direction. Divergent changes preserve both versions for explicit resolution. Modification times alone do not choose a winner. Deletions are not propagated. Establishing a new common baseline from equal observations requires a fresh local content hash and a current cloud-version check, including when local size/time are unchanged. An already confirmed unchanged baseline still takes the existing fast path.

Cloud scans, comparison and backup verification do not download business file contents. Local files use SHA-256 plus size/time caching with periodic local full checks. The upload stream is checked against the planned local SHA-256 and its QuickXorHash is compared with the cloud response. QuickXor is a transfer checksum, not a cryptographic digest; cloud-only observation cannot independently recompute SHA-256. Missing required provider checksums stop the operation with evidence retained instead of silently downloading content.

JSON metadata may be downloaded. Explicit Pull, permitted automatic download plans, and KeepLocal protection copies also download the requested content. These are not comparison downloads.

## Project automatic policy

Each projects.json folders entry may set `automaticBackupMode` to `upload`, `bidirectional` or `download`. The default is `upload`. This is a local, per-project policy, independent on each device. Upload-only work uses Backup decisions; download-only work uses conservative Pull decisions; bidirectional work chooses Backup or Pull for each file. Existing Boolean `automaticBidirectional` entries remain readable: true means bidirectional and false/omission means upload. When present, `automaticBackupMode` takes precedence. Unsupported mode values are rejected rather than silently falling back; the editor writes the explicit mode and removes the old Boolean field.

Desktop scheduling, the window/tray Run now action and CLI `backup --automatic` use this same policy execution path, including mapping readiness, pause and automatic budgets. Explicit manual upload and download actions retain their directional contracts. Policy-only edits do not change mappingVersion, binding, retired mapping snapshots, common baselines or readiness; a new physical mapping still requires a completed explicit upload/pull before automatic work starts.

Automatic bidirectional execution uses trusted current observations and the common baseline. Local-only changes upload, cloud-only changes download, and a single-sided file or directory is copied to the missing side when evidence permits. Equal files follow normal baseline verification. Unequal files without a common baseline, divergent edits, insufficient metadata and type conflicts remain for explicit resolution, with existing conflict protection retained. Deletions are never propagated; an existing counterpart may therefore restore a deleted file. Comparison never downloads business contents. A download starts only after a permitted Pull plan is selected, refreshes the local content observation, and uses the existing Pull transaction, protection, cloud-version and checksum checks before replacement and baseline commit.

All three modes share the run lock, schedule, pause control, cancellation, hard deadline and automatic transfer/time budgets. Download reservations use the incoming cloud content size; required local protection uploads also consume content budget. Download only constrains the direction of project business contents: management metadata, device observations and protection copies may still be uploaded. Automatic work retains pending transactions and skips affected paths rather than acquiring the manual retry policy. Changing the policy does not authorize unknown cloud contents or initialize a mapping.

The project editor uses a three-choice automatic backup mode selector and one cloud path relative to OneDrive root. The root is the fixed path base, while each project keeps its own relative destination; removing the redundant resolved-target display does not change storage mappings. The project list omits the resolved-target column and presents protection status as a short, single-line value with fixed row height. Full success time, restore-verification evidence and backlog details remain available through the status tooltip and More actions > View project status. A short status does not imply that unobserved contents or the whole repository were verified.

Content downloads follow up to ten redirects (301/302/303/307/308), resolving relative locations and validating HTTPS, host, port and user information on every hop. Only the initial Graph content request carries the bearer token; subsequent requests use the preauthenticated location without authorization headers and retain the staged-file Range. Cycles, missing locations and untrusted endpoints fail before copying content. The existing before/after version checks and caller checksum verification still apply to metadata and business downloads alike.

## Publication and recovery

Small uploads use a create-only content endpoint at the final path. Large uploads keep resumable encrypted checkpoints. The Graph adapter retains its tested unique-name upload-session workaround followed by a create-only rename, because some personal-drive endpoints ignored/rejected session conflict options; this is protocol-level collision protection, not a per-file protection directory.

For replacement:
1. Compare trusted metadata/common baseline, then hold the local source open and validate SHA-256 and QuickXor against the plan.
2. Save a version-5 journal bound to device, account, drive, repository, task and mapping, with the original mapping snapshot.
3. Check the live cloud version again and conditionally move it into history (or conflicts for an explicit conflict choice).
4. Upload the new complete content at the original path with create-only publication and verify the returned checksum/size; preserve the local modification time with a conditional update.
5. Normalize history to its readable original path, publish immutable metadata, then advance the common baseline.
6. Delete the completed local journal.

The target may be absent during the upload. On failure, copy the archived old file back in the cloud if the target is still empty, verify it and publish restored-version evidence. Never restore over a competing file. A lost archive, upload, restore or commit response is reconciled by identity and checksum. Interrupted restore resumes before other work. A changed source cannot resume uploading unplanned content. If the cloud is unavailable, keep the journal/history for later recovery.

If a previous historical file already occupies the readable history path, preserve it while the next predecessor is archived under an operation-owned .harbor-history-<id>.tmp name in the same directory. Only after the replacement (or rollback) is verified may the exact indexed previous history be removed and the new predecessor renamed. Normal completion leaves one historical file at the original relative path. No ordinary content directory is created under conflicts for normal uploads.

Pull downloads to a same-directory local temporary file, verifies SHA-256/checksum, checks both ends again and retains local rollback bytes until replacement is safe. Unmodified local common-baseline content is not re-uploaded, avoiding a downgrade of shared history; independent local content is protected first. Confirmed pull selections remain bound to project, local and cloud evidence.

Cloud file metadata and protection indexes remain version 2; new upload journals are version 5. Version-4 journals can still recover through their current or retained original mapping. Journals from earlier upload layouts stop with an explicit previous-release recovery instruction. Old cloud archives are preserved, not silently migrated, indexed by the new layout or deleted. Older releases reject v5 journals; finish their recovery using this release before downgrading.

Eight file operations continuously refill available slots by default; directories remain dependency barriers. The runtime's explicit concurrency argument accepts 1–8 workers for controlled comparisons; hosts use the default. An observed 429 halves the dispatch window (minimum one); sixteen successful completions allow a one-slot increase up to the configured maximum. Existing in-flight operations are drained, never abandoned. Failure stops dispatch. Metadata cache disk access is synchronized and disposable cache failures cannot fail a verified cloud transfer. Protection lookup is scoped to a single file rather than scanning all project history. Run reports include confirmed uploaded-content bytes/files, aggregate upload-call duration, aggregate file-processing duration, throttling/window reduction counts and durable local journal-write count. These are not wire traffic or measured bandwidth; durations overlap under concurrency.

## Performance and UI

- Production Graph requests and interactive authentication check network-interface availability before requesting credentials or sending HTTP. An unavailable interface fails with an explicit offline result; an available interface does not assert Internet or OneDrive reachability. Requests remain authoritative for DNS, connection, TLS, timeout and service failures. If Windows cannot query interface availability, the request proceeds normally. Injected transports remain independent of host connectivity for isolated tests.
- Ordinary Desktop messages distinguish offline, unreachable OneDrive, secure-connection failures and temporary service unavailability without displaying diagnostic exception chains. Network-only run/preview failures show a waiting-for-network status. Sanitized original diagnostics remain in stored run reports; authorization failures, cancellation and local I/O errors retain their own semantics. No connectivity result is cached as a permanent failure, and offline errors do not revoke authorization or remove pending recovery evidence.

- Directory scans are scoped to the chosen project, not the entire OneDrive. The initial drive-wide change cursor uses token=latest; a stable before/after delta fence allows inventory reuse for up to six hours. Any cloud change, full check, policy/binding change or invalid cache rebuilds the project inventory. This invalidation cache is not a write precondition or a deletion synchronizer.
- Inventory snapshots live in cache/cloud-inventory; successful per-device observation fingerprints live in cache/cloud-observations. Both are disposable. Changed observations publish immediately, identical observations at most once per hour. Transaction file-version records remain immediate. Failed observations remain in state/devices/<device>/cloud-outbox until verified publication.
- Concurrent HTTP requests share host-scoped throttling deadlines, use Retry-After or jittered exponential backoff, and remain cancellable. Ambiguous failed writes are left for journal reconciliation; only reads and explicit 429 rejections are automatically retried.
- Structured run metrics include cloud requests, retries, wait duration, listing/cache counts and scan/read duration. A single-value progress mailbox prevents per-file UI queue growth.
- Shared metadata is loaded once per scan and grouped by path; file operations do not repeatedly load the full revision graph.
- Immutable metadata is cached by item ID and ETag. Verified metadata uploads populate that cache.
- Management folder IDs are reused within a session; local hash cache is disposable, baselines are not. Unreadable or locked hash/observation-acknowledgment caches cause fresh observation/publication without failing a verified transfer. Cache writes are best effort; outbox records remain strict recovery state and are removed only after verified cloud publication, independently of acknowledgment-cache success.
- Per-file baselines avoid rewriting a giant baseline document for every file.
- UI reports metadata reading, local scanning/hashing, upload, protection, verification and publication.
- Each project offers cloud folder browsing and a truthful final path. Management settings no longer contain a global backup-content directory.
- The Desktop project-folder picker shares a bounded, five-minute in-memory listing cache within the desktop session, isolated by account settings and folder ID. The configured folder opens directly when its ID is known; otherwise browsing starts at the root. Requested listings are displayed before limited child-listing prefetch (at most eight folders, two concurrent reads); prefetch does not recursively scan OneDrive. Navigation reuses successful listings and coalesces concurrent reads for the same folder. Explicit refresh bypasses cached results; failed reads preserve the current location and successful listing. Closing the picker cancels its pending reads, and account changes discard obsolete responses. This cache is only for navigation: it does not establish baselines or replace execution-time cloud identity/version checks.

Cloud folder names and modification times are preserved where supported. NTFS ACLs, alternate streams and reparse-point semantics are not represented as ordinary OneDrive files.


## Streamlined normal upload path

Execution-mode local scans defer uncached/expired content reads to the bounded workers. Each worker opens and locks its source, computes SHA-256 and QuickXor in one pass, reevaluates the decision, and reuses that handle through upload and metadata commit. Both checksums enter the initial v5 Prepared journal, eliminating a separate rewrite of unchanged checksum evidence. Recovery still calculates and persists a missing QuickXor before remote mutation. Previews retain full observation behavior; unchanged valid cached content still avoids hashing.

File metadata is loaded with at most four concurrent reads, preserving the listing's ordering for equal-time revisions. Cache-hit and read counters are synchronized. All reads are drained before returning on cancellation/failure; no transfer can start from a partial observation. Pull computes SHA-256 and QuickXor in one sequential read of the downloaded temporary file, and retains the final live-cloud/local-baseline checks. Cloud file layout, metadata formats, protection and journal phases are unchanged. These changes reduce waits and local I/O; they do not remove the per-file upload, modification-time and metadata requests, nor constitute a real-account throughput measurement.

## Network request reuse and scoped observation

Each observation and explicit recovery resets its repository directory cache. Within that operation, successful read-only and create resolutions share folder IDs; missing directories are not cached. Target validation reuses common ancestors within its validated traversal. Registration validates its already-read location records rather than immediately loading them again; the initial observation and completion still perform independent location listings. Device observation publication shares the operation's repository directory cache. Writes retain their create-only/If-Match semantics; cached folder evidence never replaces business-file version checks or recovery identity validation.

Immutable JSON creation attempts a create-only upload first. Only an explicit 409 triggers lookup and mandatory size/content verification of the existing record. Ambiguous failures are not automatically replayed. Payloads, cloud layout and transaction phases are unchanged.

Inventory cache schema 2 stores business/metadata root IDs and observed directory identities. Detailed drive delta changes invalidate a snapshot when relevant file identity/version or directory structure changes, or when scope cannot be proven. Unknown deletions, missing parents, cycles, expired cursors and unavailable details cause a full project observation. Unrelated changes, including device observations, may advance the cursor without extending the original six-hour full-observation deadline. Ancestor folder tag changes alone do not invalidate; names and parents must still match. Delta remains an observation optimization, never a write authorization. Prior cache files are disposable and rebuilt; state is untouched.

Uncached file JSON metadata may be read in groups of at most 20 items and 64 MiB total, with each item still limited to 32 MiB. Before/after version GETs use read-only Graph batches; content reads retain validated redirects and token boundaries, with at most four concurrent bodies. Responses are correlated by request ID, individually checked and retried on explicit throttling/transient read failures. Every body's size and the before/after ETags must match the listing. All reads drain, and all JSON values parse, before cache population and subsequent decisions. Malformed, missing or changed evidence cannot produce a partial transfer plan. HTTP request counts include batch envelopes, not the count of logical GETs inside them.

Upload-session chunks default to 10 MiB, configurable in the transport for controlled comparisons within 320 KiB–20 MiB and always a multiple of 320 KiB. Resume offsets retain their 320 KiB alignment independently of the current chunk size. The staging-name/create-only publication protocol remains intact. Real-account comparisons and limitations are recorded in the development network optimization report; they are not installation acceptance.

Cloud folder IDs from the project inventory are reused for the run. Created parent folders are cached. Normal creates and new immutable metadata write directly with create-only collision handling instead of repeated preflight GETs. Conditional archive moves use the scanned ID/ETag; failed/lost responses are reconciled separately. A successful normal upload records the acknowledged hash without another cloud lookup/local hash. Recovery and Pull still verify current evidence.

In the stable, initialized, small-file path, the adapter needs PUT content, PATCH modification time, PUT file metadata: three writes and no per-file GET. Authorization, inventory/setup, protection, missing provider checksums, observation publication and retries are separate. This reduces round trips; it is not a production speed claim. Version-5 journals include the mapping snapshot described above; version-4 recovery remains supported.

## Recovery isolation and history details

Pending discovery is restricted to the current device. Journals with a verified original mapping and relative path affect only overlapping files; older ordinary-tree journal versions 2/3 no longer cause a global format exception. Version 3 can be scoped but cannot be replayed without its format contract. Unknown formats, invalid identities and unavailable original mappings retain their evidence and produce a persisted failure report, including the affected record location when available. They never authorize a write. Configuration saves remain independent.

Explicit recovery of version 2 closes the old staged-upload operation rather than replaying it as a direct upload. It verifies stage/archive identities, parents and provider checksums. If archival left a gap in the business tree, it restores the verified original with a conditional create-only move; lost responses can be reconciled. A published staged item is verified in place. The original journal is moved without overwrite to `state/devices/<device>/cloud/<binding>/retained-transactions/<id>.json`. Old numeric protection folders, local rollback files and metadata are retained. Recovery does not commit an inferred common baseline; the user uploads or pulls again with current configuration. Unsupported or changed evidence remains pending with an actionable result; one recoverable journal can finish even when another fails.

Run history opens an owned, read-only details dialog. Closing it preserves the history page, filters and selection. The dialog provides full selectable text, search and an attention filter. The issues page only displays attention rows from the latest result; opening an old report cannot replace them. Preview and issues also provide full-text detail dialogs.

## Manual retry of an interrupted upload

Manual unconfirmed Backup retries current-mapping Backup journals, and explicit recovery retries Backup journals belonging to active mappings. Automatic backups, readonly previews, confirmation-bound selections and retired mappings do not silently acquire this local-preference policy. Pull recovery retains its own contract.

After validating device/task/mapping/path/format, retry copies the exact original journal bytes into retained-transactions without overwrite. The active intent stays discoverable until cloud reconciliation completes. An updated recovery phase can retain another immutable snapshot; upload sessions and temporary stages are kept. Retry never requires the current source to match the old source hash.

The adapter inspects the live target, recorded uploads and the original archive, including a lost archive receipt or a completed upload with a lost receipt. A verified archived original gets an independent conflict protection copy before ordinary history may rotate. Its protection index is reconciled without deleting the old materials. A business-tree gap is restored through journaled create-only recovery before a fresh upload begins. A competing live version is left in place for the fresh upload's normal pre-replacement protection; rollback never overwrites it. Invalid identities, unavailable source content, file/directory collisions and unverifiable archives stop safely with evidence retained.

After reconciliation, retry reads current cloud/local evidence, locks and hashes the current local source, and uses the explicit local-upload decision. The ordinary transfer pipeline protects different cloud content, uploads and verifies current bytes, publishes metadata and only then commits their common baseline. It does not commit an inferred baseline for the retired upload. If this fresh upload is interrupted, a new active journal remains retryable and the original snapshot stays retained. Closing an obsolete intent alone is not reported as a completed upload.

Low-level recovery callers without the explicit retry policy can still retire a changed unpublished source intent only when the business target is unchanged and there is no recorded protection/upload/commit. That conservative branch does not upload business content or establish a baseline.

## Pull retry within the normal operation

A validated v2/v4/v5 Prepared pull with no original local content, protection, uploaded/staged content, incoming version or commit is an unwritten download intent. If the current local file is still missing, the ordinary pull preview offers it as a selectable download. Preview does not modify the journal or business files. The selection confirmation incorporates the original journal signatures as well as the newly observed local/cloud evidence.

After a confirmed selection is revalidated, execution retains the exact original record under retained-transactions and starts a fresh pull from the current cloud version. Unselected records and partial temporary files remain untouched. A directory switch can supersede the old read intent for the same task and destination without writing the old source. Missing parent directories can be created by the confirmed pull. A second interrupted download remains retryable under the same rule. Backup, written/protected pulls, changed identities, unknown formats and newly present local contents are not automatically superseded.

The preview presents user-facing transfer/protection descriptions and counts a blocked file once, without counting its project-level pending summary again.

## Workflow boundaries

- File journals, protection and verified common baselines determine transfer completion. A completed manual mapping is marked ready before optional per-device observation publication. Publication failures remain visible as nonfatal DeviceStatusPending issues and keep their outbox evidence; they do not revoke readiness or stop another project under the fail-on-error policy.
- Pending discovery returns valid files and separate diagnostics. A valid binding directory or validated original mapping scopes unreadable evidence to overlapping cloud/local locations. Unknown scope remains conservative. Preview, execution and explicit conflict inspection use the same scope. Evidence is neither deleted nor reinterpreted by this diagnosis.
- Configuration loading is independent of scheduler, last-run and history display reads. Desktop keeps the configuration and project controls available, displays state diagnostics separately, and pauses automatic work if the scheduler record cannot be verified. A malformed readiness marker means another manual operation is required; a successful manual operation can establish new readiness.
- Saving retention preferences for an unchanged bound repository writes local configuration only, including offline or reauthorization states and when journals exist. Actual rebinds retain authorization, repository validation, immutable layout and recovery guards. The account dialog retains the saved repository selection when browsing fails.
- Cloud project catalog reads use their own cancellation and captured account settings, without occupying the operation coordinator. Existing account-change checks discard obsolete catalog results; cache writes remain disposable and synchronized. Slow catalog reads do not disable local project editing or configuration saves. File execution and configuration commit locks remain in place.

## Protocol references and verification

### Project identity

The installer automatically checks local project, account and current-device run-state formats while holding its maintenance lease. It invokes the installed helper before releasing maintenance or launching the app. Fresh and unsupported configurations are regenerated; the entire original data tree is retained. Current-format data is unchanged. An unpredictable per-installation lease plus maintenance, startup and run locks prevents the helper from being used during normal application lifetime. Source availability and cloud connectivity do not affect this format check. I/O failures abort installation and retain the original data instead of forcing a reset. Manual initialization is not required.

The project ID from configuration is authoritative for the catalog, joins, list merge/selection/removal, file metadata, observations, protection indexes, run status and confirmation selections. A join copies this ID to the new device. Location revisions use mapping identity and an increasing generation; generation ties are ordered by mapping ID. Old location records remain immutable; an unchanged old mapping cannot republish itself over a later location. Folder IDs validate the current physical target and do not identify the logical project. Names and paths remain display/transfer properties.

Dismissed cloud projects are scoped by drive/repository/management root/project ID. Catalog filtering does not consult retired recovery mappings or compare paths. Project settings use schema 2, protection records and status use schema 3. initialize --fresh holds the maintenance/startup and run locks, refuses active applications, stages empty settings and retains the entire old local data tree without migration. It performs no cloud operation.
