# 普通目录备份调整方案与问题核查

状态：0.9.0-preview.1 已实现代码与隔离验证；正式安装、配置及原有云端备份未改动。当前执行规则见 [账户传输架构](onedrive-account-transport.md)。用户补充要求：普通历史只留上一份；比较只用元数据，缺少可信元数据的已有文件先保留，由用户明确取回建立基线。下文问题核查为修改前的诊断记录。

## 需求依据

对照旧项目 `AutoBackup/README-zh.md`、`scripts/Backup-Conflict.ps1`、`Backup-Sync.ps1`、`Backup-FileStore.ps1`：
- destination 相对 OneDrive 根目录解析，直接保存原文件树，不额外拼接电脑名、项目摘要或版本 ID。
- Backup 仅写目标，Pull 需明确操作且仅写源；不传播删除。
- 覆盖前保护不同内容，复制核验完成才提交基线。
- 全局与项目排除取并集，缓存有周期性内容核查。
- 旧冲突策略以修改时间选较新者，同时间不同内容待处理；初次不同内容或双方修改需保护副本。

用户最新要求：备份正文独立指定位置；OneDrive/HarborBackup 可存元数据、历史版本和冲突副本。继续使用授权账户 API 传输，不恢复依赖本地同步目录的执行链。

## 目录与界面

示例：
```text
OneDrive/
├─ Projects/
│  └─ DROP_CODE/                 # 此项目指定的目标
│     ├─ building_obstacle_index.py
│     └─ docs/
└─ HarborBackup/
   ├─ metadata/                  # 项目映射、设备观察、共同版本信息
   ├─ archives/                  # 覆盖前的历史版本
   └─ conflicts/                 # 未解决冲突副本
```

- 每个项目选择最终云端文件夹，或输入相对 OneDrive 根的路径。例如 Projects/DROP_CODE 就是最终目标，不再隐式追加 HarborBackup/backups。
- 本地绝对路径只用于源目录。云端记录 driveId + folderId，显示真实云端路径；不可依赖其他电脑的 C:\\Users 路径。
- 备份正文的文件名、相对目录、内容保持原样；保留可支持的修改时间。不可承诺 NTFS 权限、链接、备用数据流等均可由 OneDrive 原样表示；不支持项预览中明确报告。
- 现有普通非空目标允许预览和比对，不再按“专用仓库必须为空”拒绝。首次接管不盲目覆盖不同内容。
- 元数据和保护目录可独立配置，默认置于 HarborBackup 下。项目目标之间及与管理目录之间禁止危险重叠。
- 设置保留一个账户管理入口。项目编辑增加云端目标浏览、新建和清晰的最终路径；不显示虚构目录。
- 数字标识只用于元数据和版本证据，不替代备份正文目录。
- 本机配置、授权凭据、恢复事务仍放安装目录 data；凭据和本机路径不共享。

## 冲突与安全提交

建议保留旧脚本的使用方式，并增强多设备判断：
1. 内容相同：不重复传输，确认共同基线。
2. 仅源改变：先保护云端旧内容，再上传并核验。
3. 仅云端改变：自动备份标为待取回；用户明确取回后保护本地旧内容再替换。
4. 双方改变或首次不同内容无可靠基线：保留双方，等待明确选择；不单凭电脑修改时间静默裁决。
5. 文件缺失：不推断删除；不传播删除。
6. 提交前复查云端版本，使用经过验证的条件写入，处理并发修改；禁止“先检查再无条件覆盖”。
7. 不确定上传结果先按事务和文件身份核对，不能当作成功、盲重试覆盖或清除恢复证据。
8. 只有实际传输和核验成功才更新共享结果及本机共同基线。

第 4 条是对旧脚本“较新时间优先”的建议改进。旧算法本身并不能可靠消除设备时钟差与并发写入问题。

云端 API 的条件上传、分块最终提交、云端归档复制和中断恢复须分别验证，不能将创建上传会话时的检查当作整个传输期间的互斥。多设备不能共享一个反复覆盖的大 JSON；采用按设备/操作隔离的记录并检测并发。

## 本次已确认的问题

- 项目编辑与列表显示 HarborBackup/backups/项目名，但真实实现为 backups/项目摘要/版本 ID/...。显示与存储含义不一致。
- 正式日志的第二轮备份已完成 3 个文件，随后用户停止；扫描统计 17,405 个文件、1,206,871,874 哈希字节、17,417 个条目。
- 第三轮失败为 A managed cloud version changed outside HarborBackup。
- 只读核对 4 个云端修订：3 个文件大小、ETag、SHA-256 均一致；docs 是目录，ETag 与修订记录不同。ReadAsync 对目录也要求原始 ETag 相等，是此次失败触发条件。目录版本判断不应套用文件内容不变规则。
- ReadAsync 强制对本地文件完整哈希，未使用设置中的缓存策略；处理阶段报告没有传 HashedBytes，因此界面长期显示 0.0 MiB。
- 处理一个文件时多次读取全项目修订，清单缓存又触发整个 drive 的 delta 检查；首文件及小文件开销明显，需要项目批次内聚合、增量索引及并发边界复查。
- 当前进度缺少上传、校验、提交阶段，HTTP 等待时没有明确可观察状态。
- 项目扫描/云端观察阶段的部分异常直接终止整个项目，后续需完善单文件错误隔离，同时不跳过与恢复安全相关的错误。

只读诊断没有修改正式配置、源文件和云端文件；临时授权副本保持 Windows 用户加密，结束后已删除。

## 开发顺序

1. 冻结格式与项目目标语义：独立目标、管理根、保护位置、项目跨设备身份和目录重叠校验。
2. 建立普通目录云端扫描与三方比较，支持已有非空目标、预览、排除和缺失文件。
3. 完成受条件保护的上传、覆盖前保护、取回和恢复；验证多设备竞争。
4. 整合元数据、缓存和批次查询；添加阶段、文件数、字节数、网络等待、取消进度。
5. 更新项目编辑、账户设置、日志与中英文帮助；路径必须与真实位置一致。
6. 隔离验证通过后发布安装包。旧数字版本内容保留；迁移必须先预览冲突和完整性，不自动删旧内容或重新选择胜者。

## 验收

- 指定目标下可直接打开原文件，不需要 HarborBackup 解包。
- 子目录、空目录、中文/空格、长路径、排除规则一致。
- 已有普通目录不强制清空；相同内容免重复上传，首次不同内容安全处理。
- 双设备同文件、云端手动修改、仅元数据变化、目录 ETag 变化。
- 小文件集合、大文件、断网、节流、令牌失效、取消/超时、丢失提交响应、中断恢复。
- SHA-256 校验失败、保护失败不得覆盖或提交成功。
- 缓存命中和定期完整核查实际生效，进度不再伪报零哈希量。
- 完整回归测试通过不等于真实双设备和实际安装验收通过，分别记录。
