# 真实 OneDrive 业务流程耗时分布（2026-11-18）

## 结论

小文件场景的主要开销来自多次云端访问。即使没有文件变化、清单和文件内容缓存都命中、设备状态也无需上传，完整 Backup 仍耗时 **21.065 秒、25 次 HTTP 请求**。其中 12.517 秒用于观察云端，8.523 秒用于后续文件处理和映射确认。本地扫描为 4.61 毫秒。

修改两个 8 KiB 文件的备份耗时 68.487 秒、70 次 HTTP 请求；两次正文上传 API 调用累计仅 2.431 秒，更多请求来自目录准备、历史保护、身份/版本核验和元数据。API 累计时间可能重叠，不能直接从总时长扣减。

本轮只做测量，没有修改产品传输策略、默认并发或缓存规则。

## 范围与计时口径

- Windows、.NET SDK 10.0.115、Release；产品源码基点 `5089436228713b1a157ed00de3f092688d36c147`。工作区包含先前未提交的测试及文档，提交号不代表完整工作区快照。
- 使用真实已授权的个人 OneDrive 账户，在随机命名的 `HarborBackup-flow-test-*` 测试根目录中操作。管理区与业务目标分开。
- 4 个 8 KiB 随机合成文件，放在 2 个子目录中；随后修改其中两个文件。默认四路文件并发，目录仍遵守现有调度屏障。
- A、B 为同一台机器上的独立源目录和本地状态目录，模拟两个设备身份，不是两台实体电脑。
- 全程调用实际 CloudBackupRuntime 的 PreviewAsync / ExecuteAsync，包括恢复记录检查、云端读取、本地扫描、决策、处理、共同基线/映射就绪、状态发布及本地运行报告。
- 表中从业务用例入口计时到返回；授权预热、测试根/管理区准备、清理单独执行，不计入用例时间。首次授权预热耗时 1.578 秒，没有交互登录。
- 粗阶段按同步进度事件分界：ReadingMetadata 开始云端观察；之后的 Scanning 开始本地扫描；第一个 Processing 开始文件处理；Publishing 开始设备状态发布。预览没有 Processing，扫描列包含其后的本地决策与结果构造。
- “文件处理及映射”包含本地哈希、事务落盘、历史保护、上传/下载、修改时间、校验、文件元数据、基线和项目注册确认，不等于正文传输。
- “状态发布及报告”包含设备观察元数据发布和本地状态/历史/日志写入，不等于本地报告写入很慢。
- HTTP 时序从请求开始到响应正文读完或释放，包含上传、重定向、响应正文读取；并发请求取时间区间并集，得到真实墙钟中的请求在途覆盖时间。它包含少量客户端响应处理，不等于独立测得的纯服务端执行时间。
- 同时记录 ICloudDrive API 调用来源、各调用耗时、取令牌耗时以及匿名化的重复 GET 端点。未记录 bearer token、预授权 URL 或真实业务文件路径。

单位：秒。各阶段按墙钟划分，不相互重叠；不足 0.01 秒的入口检查及四舍五入差异没有单列。

| 03 紧接着第二次无变化备份 | 29.560 | 34 | 21.588 | 0.003 | 7.952 | 0.016 |

| 05 两个文件修改后的上传预览 | 18.691 | 15 | 18.658 | 0.027 | — | — |
| 06 修改备份，保护旧云端内容 | 68.487 | 70 | 18.343 | 0.003 | 41.580 | 8.560 |

9 个用例均退出码 0，共 425 次 HTTP 请求。加上测试准备与清理共 435 次请求，无 429、5xx 或传输异常。每个场景的 HTTP 在途区间并集占用例墙钟时间的 **98.73%–99.40%**。取令牌 API 调用累计耗时每场景为 0.104–0.368 秒，当前样本没有显示授权缓存占据秒级主开销。

每个场景一次测量，按表中顺序执行；网络时延随时间变化，不能把不同场景的耗时差全部归因于代码差异。例如场景 04 和 05 都有 15 次云端观察请求，但观察耗时不同。

## 固定校验与目录访问

稳定无变化 Backup 的 25 次请求均为 GET，没有正文传输、元数据上传或状态上传。

| 调用来源 | API 调用次数 | 调用累计耗时（秒） |
| --- | ---: | ---: |
| CloudRepository.FolderCoreAsync 逐级查找管理目录 | 12 | 10.532 |
| CloudRepository.ValidateTargetAsync 读取目录/祖先项 | 5 | 4.015 |
| CloudProjectRegistry.ReadAsync 枚举项目位置记录 | 3 | 2.031 |
| 读取 repository.json 项信息 | 1 | 1.202 |
| 读取项目目标项 | 1 | 0.944 |
| 读取云盘根目录 | 1 | 0.826 |
| delta 检查 | 1 | 0.792 |
| 读取管理根目录项 | 1 | 0.656 |

此场景串行程度很高，API 累计值接近墙钟时长。3 次项目位置读取各包含逐级目录查找和 children 枚举。源代码调用关系为：观察中的 ValidateAsync 读取一次；完成映射时 RegisterAsync 先 ReadAsync，已有映射时再调用 ValidateAsync，产生另外两次读取。FolderCoreAsync 的只读分支不复用 create 分支的路径缓存，因此这些路径被反复查找。

与前一轮仅调用 CloudBackupSession.ReadAsync 的 15 次请求相比，这次完整 Backup 额外包含 10 次映射确认请求，说明只测读取或正文上传不能代表完整业务耗时。

本轮稳定无变化场景中，按匿名 URL 指纹统计有 13 次重复 GET。重复不等于全部可以移除：版本前后核验和并发身份验证有语义要求，优化仍需保留相应边界。

## 元数据冷启动与拉取

新设备拉取预览没有下载业务正文，但读取了 8 份 JSON：仓库标记 1、项目位置记录 1、文件元数据 6。文件元数据为首次 4 份加修改后的 2 份不可变记录，当前业务文件仍是 4 个。

这 8 次 DownloadMetadata API 调用产生 **40 次 HTTP 请求**：每份 JSON 都有下载前后项版本 GET、Graph content GET，以及本次链路上的两次内容域请求。其 HTTP 耗时累计 30.736 秒；文件元数据读取存在并发，因此不能将累计值直接理解为串行等待。加上目标验证、目录和 delta 请求，预览合计 64 次、37.425 秒。

确认后拉取重新观察当前证据，清单和 6 份文件元数据缓存命中；这一环节仍有 15 次 HTTP 请求、13.829 秒。随后 4 次 DownloadBusiness 调用包含其内部版本检查和重定向，共产生 20 次 HTTP 请求。其余请求来自外层重新查找、保护/提交检查、项目位置注册及管理元数据发布，完整拉取合计 77 次、48.218 秒。

拉取后的 4 个本地文件均独立计算 SHA-256，并与预期合成内容匹配。Pull 没有改写云端业务文件；管理元数据发布属于用例既有行为。

## 状态发布与下一轮扫描

首次备份后的第一次无变化备份会把结果从 Copy 等变为 Equal 等，导致设备观察指纹改变。本轮实际发布了新的设备观察记录，增加了 7 次 HTTP 请求、约 5.964 秒的状态发布及报告阶段。

紧接着的第二次无变化备份跳过状态发布，却仍因上一轮云盘变更而重建清单，云端观察为 24 次请求；第三次才命中清单缓存，下降到 15 次。这说明无关管理状态变化也会影响下一轮扫描，是前一轮缓存失效范围问题在完整执行链中的体现。

## 优化验证的优先级

1. 评估一次运行中复用已验证的项目位置及目录路径证据，避免重复走完整目录链；保留真实身份变更和并发写入前的必要复核。
2. 缩小清单缓存失效范围，区分业务内容/文件证据变化和设备状态上报等无关变化；不能只凭云盘发生任意变化就扫描全部项目。
3. 评估首次加载 JSON 元数据的请求组合：当前 8 份 JSON 产生 40 次请求，优化须保留版本一致性、重定向及令牌边界。
4. 评估保护与元数据目录准备的复用，以及设备状态发布的固定成本。单纯调整正文并发或分块不足以解决这些等待。

上述为基于真实时序和代码调用关系的候选方向，尚未实现或测量其优化后收益。
