## PersonalProjects → MyProjects 的实测结果

`ProjectFolderRenameTransferTests` 使用真实 `ConfigurationEditor.Save` 流程、独立临时目录和合成云盘。先完成初始备份，再实际重命名本地或云端目录并保存配置，重新创建运行时进行预览和执行。项目 ID 保持不变，映射版本及绑定确实改变。

每个场景有 28 个业务文件，共 2765 字节，包含空文件、业务 `.json`、二进制及多层目录。18 个纯改名场景覆盖：

- 项目根目录改名与项目父目录改名。
- 仅本地、仅云端及两侧同时改名。
- 独立的上传确认执行和下载确认执行。
- 保留缓存或删除隔离缓存；保留云端目录 ID 或模拟手动输入路径清除该字段。
- 文件 ETag 改变而 ContentTag 及内容证据保留。

18 组预览及执行均为 **业务正文上传 0 文件 / 0 字节，下载 0 文件 / 0 字节**；保护正文及未分类正文传输也均为 0。业务文件身份与内容保持不变，没有新增保护副本。

对照结果如下，所有预览阶段均未传输业务正文：

| 场景 | 执行业务上传 | 执行业务下载 | 其他内容保护 |
| --- | ---: | ---: | --- |
| 改名后仅本地一份文件改变 | 1 文件 / 44 字节 | 0 | 旧云端版本通过云端移动保护 |
| 改名后仅云端一份文件改变 | 0 | 1 文件 / 44 字节 | 独立本地旧内容上传保护 34 字节 |
| 仅改配置指向实际为空的新云端目标 | 28 文件 / 2765 字节 | 0 | 旧目标及其内容保留 |
| 复制到新云端目录，产生新文件 ID，再明确确认上传 | 28 文件 / 2765 字节 | 0 | 28 份被替换的云端正文先受保护 |

复制产生新 ID 的对照中，普通只读比较先返回 `CloudMetadataRequired`；显式上传预览才变为复制计划。原目录改名与复制到新物理文件身份具有不同证据条件，不能混用结论。

### 扫描、哈希与正文传输的区分

代表性的双方父目录改名场景，预览报告的本地哈希量为 2765 字节。确认上传执行报告为 5530 字节、56 次哈希，业务正文上传和下载仍均为 0；它包含源内容准备和建立新映射共同基线前的重新核验。确认下载执行报告的哈希计数为 2765 字节；该指标未合并每次额外本地刷新读取，不能当作精确物理 I/O 总量。

仍存在管理元数据读写。保留元数据缓存的代表上传执行写入 2 份管理 JSON；清空缓存的代表预览读取 30 份管理记录，业务正文下载仍为 0。`FakeDrive.BodyTransfers` 在实际成功流读写时记录身份和字节，并按业务、保护和管理子树的 ID 分类，不以扩展名或 `Documents` 等目录名判断正文。

因此本次隔离测试没有复现“仅改名导致相同业务文件重新传输”，确认会发生新映射的重新扫描与哈希。实际更换为空目录或复制后失去原文件身份时，明确确认的上传会传输这些文件。
